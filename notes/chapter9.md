# 第九章教学笔记：知识增强RAG（Knowledge-Enhanced RAG）

（依据《Hands-On RAG for Production》第九章原文 + `chapter9/` 下的 notebooks 整理）

RAG把信息检索从死板的关键词匹配，带入了更流畅、更直观的语义搜索领域——能按概念含义而非具体字词找文档。但纯向量检索或混合检索，面对"需要精确理解实体之间关系"的查询依然会力不从心，因为**向量搜索处理的是概率和相似度，不是确定性的事实**。第九章讲的就是这个局限，以及知识图谱（KG）如何补上这一课。

---

## 一、向量/混合检索的三个固有局限

书里用三类具体例子说明语义检索为什么在这些场景下会失败：

1. **时间限定的事实（Time-bound facts）**：语义搜索不擅长回答依赖具体时间点的问题，因为embedding会把过去和现在的信息模糊地混在一起。比如问"2022年10月谁是推特CEO？"，可能会返回同时提到Elon Musk、Jack Dorsey、Parag Agrawal的chunk，却没有任何明确的时间对齐——这通常导致一个糟糕的回答，或者LLM干脆把几个选项都列出来，而不是精准定位到2022年那个正确答案。（书里也提醒，近期的高级语义搜索实现，比如**过滤式ANN（filtered ANN）**，有时能通过按日期过滤来处理这类问题。）

2. **多重约束的交集（Intersection of multiple constraints）**：当一个问题需要同时满足不止一个条件时，语义搜索倾向于找出"松散相关"的文本，而不是保证真正的交集。比如问"哪些药物会同时和华法林、西柚汁相互作用？"，语义搜索可能捞回讲华法林相互作用的chunk，或者讲西柚汁相互作用的chunk，但未必有一个chunk同时覆盖两者。这种情况下，只有当"恰好某一个被检索到的chunk同时讨论了这两者"时，RAG系统才能给出准确答案。

3. **链式/多跳推理（Chained or multi-hop reasoning）**：向量搜索处理的是话题相似度，而不会沿着一条关系链一步步推理。比如问"2014年那部电影，导演也执导了《盗梦空间》，谁是这部电影的主演？"，向量搜索可能返回讲《盗梦空间》的chunk（其中可能提到克里斯托弗·诺兰或他的其他作品），但LLM未必能可靠地把这些线索串联成"克里斯托弗·诺兰→《星际穿越》→马修·麦康纳"这样一条完整的推理链。

书里也提醒：AI智能体（第七章讲过）理论上有能力通过把查询拆解成子查询、迭代使用工具来完全解决这些场景。但本章要探讨的是另一条路：**在不依赖AI智能体的前提下，有没有办法提升RAG检索的准确率？** 答案是**知识图谱（KG）**。**只有当这类复杂查询确实频繁出现、且它们得不到高质量回答会实质性影响业务结果时，构建和部署KG的生产复杂度才是值得的。**

## 二、知识图谱：概览

知识图谱是一个用机器可读形式编码事实知识的、相互连接的实体网络。核心组成是**节点**和**边**：

- **节点（Nodes / 实体）**：代表现实世界的物体、人、地点或概念。以IMDb数据集为例，节点包括`Movie`、`Person`、`Genre`、`Character`等。节点通常还带有**属性**（比如一个Movie节点可以有"发行年份"这个属性）。
- **边（Edges / 关系）**：节点之间的连接，定义它们如何相互关联。以IMDb为例，边可以是`ACTED_IN`、`DIRECTED`、`HAS_GENRE`、`BELONGS_TO`、`APPEARS_IN`或`MENTIONS`。

书里用一个电影知识图谱的例子说明：`Person`节点（克里斯托弗·诺兰、克里斯蒂安·贝尔、希里安·墨菲、莱昂纳多·迪卡普里奥）通过`ACTED_IN`/`DIRECTED`边连接到`Movie`节点（《奥本海默》《黑暗骑士》《盗梦空间》《泰坦尼克号》）。

**查询知识图谱和查询向量库的思路完全不同**：向量搜索是找相似度，KG查询是**沿着一条已知事实/实体组成的路径去遍历**。要回答"2014年那部由《盗梦空间》导演也执导的电影，谁是主演？"这个多跳问题，可以做一次结构化查询：先找到`Inception`节点，沿`DIRECTED`边反向遍历找到`Christopher Nolan`，再沿他所有的`DIRECTED`边遍历找到他执导的所有电影，从中筛出2014年那部，最后沿这部电影的`ACTED_IN`边找到主演。**这个例子说明了为什么搜索节点能提供精确结果，回答语义搜索难以完成的问题。**

### 如何查询知识图谱

**图数据库**是一种专门的NoSQL数据库，用图状结构存数据，强调数据点之间的关系。不同于用行列组织数据的关系型数据库，图数据库用节点和边表示图数据，专为高效执行图查询而设计。主流图数据库包括**Neo4j**、**Amazon Neptune**、**Kuzu**、**TigerGraph**。要和图数据库交互取数据，需要用图查询语言，比如**Cypher**或**SPARQL**。

**Cypher**：最初为Neo4j开发，语法直观、高度可读，视觉上贴近图结构本身。节点用圆括号`()`表示，边（关系）用方括号`[]`表示。比如"找出执导了某部电影的人"这个模式写作：

```cypher
(p:Person)-[:DIRECTED]->(m:Movie)
```

其中`(p:Person)`选中所有标为`Person`的节点（变量名`p`），`(m:Movie)`选中所有标为`Movie`的节点（变量名`m`），`[:DIRECTED]`描述边、指定关系类型为`DIRECTED`，`->`指示关系方向。完整查询检索出执导《奥本海默》的人的名字：

```cypher
MATCH (p:Person)-[:DIRECTED]->(m:Movie)
WHERE m.title = 'Oppenheimer'
RETURN p.name
```

这个查询告诉数据库匹配指定模式、按电影标题是`Oppenheimer`过滤、返回找到的Person节点的`name`属性——结果是"Christopher Nolan"。

**SPARQL**：**资源描述框架（RDF）三元组存储**（一种特殊类型的知识图谱）的标准化查询语言，用声明式模式匹配语法查询**三元组**——由**主语（subject，被描述的资源）**、**谓语（predicate，属性或关系）**、**宾语（object，值或相关资源）**三部分组成的陈述。用SPARQL写同样的《奥本海默》导演查询：

```sparql
SELECT ?personName
WHERE {
  ?movie :title "Oppenheimer" .
  ?person :directed ?movie .
  ?person :name ?personName .
}
```

`?person`、`?movie`、`?personName`是变量，`WHERE`子句里每一行都是数据库必须匹配的三元组模式。SPARQL不如Cypher视觉上直观，但作为W3C标准，是查询链接数据的强大工具，设计上更侧重"精确指定你要什么数据"而非"探索图论"。**两者实际用哪个取决于你的图数据库支持什么、你更习惯用哪个**——本章后续例子都用Cypher，但换成SPARQL同样可行。

### 本体（Ontology）与模式（Schema）

**本体**是你领域的形式化、抽象模型，定义你的知识图谱的"现实规则"——它不关心具体的数据点（比如"Christopher Nolan"这个具体的人），而是定义类别以及这些类别之间如何交互的逻辑约束。比如在电影领域，本体规定"一个Person可以`DIRECT`一部Movie"，但"一部Movie不能`DIRECT`一个Person"，还规定Movie必须有发行年份等等。

**模式**是本体在数据库层面的具体实现——你施加到图数据库上的具体标签集、关系类型、数据约束，让系统知道该如何存储和索引数据。比如如果本体规定电影有发行年份，模式就定义`Movie`节点上必须有一个叫`release_year`的属性，存成整数类型。

**在RAG里配合使用时：本体帮LLM理解数据的逻辑（"要找一个导演的作品，我必须遍历Movie节点"）；模式则是你提供给LLM（通常以文字描述形式）的东西，让它能生成正确的Cypher或SPARQL代码去查询这些数据。**

## 三、在RAG中使用知识图谱

书里用两个互补的数据源，扩展电影领域的例子，构建一个电影知识图谱：**IMDb**（提供电影的验证过的"谁、什么、何时"基础节点和关系数据，如`Movie`、`Person`、`Character`、`Genre`，属性如发行年份、角色等）和**MovieSum数据集**（HuggingFace上的电影剧本数据，包含对白和场景描述，切分成文本chunk填充`Chunk`节点）。

### 构建电影知识图谱：步骤

1. **安装Neo4j并建立账号**（其他图数据库也可以）。
2. **处理剧本文本**：先清理XML标签，再用LangChain的`RecursiveCharacterTextSplitter`切成chunk：

```python
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=CHUNK_SIZE, chunk_overlap=CHUNK_OVERLAP, length_function=len, is_separator_regex=False,
)
cleaned_script = re.sub(r'<[^>]+>', ' ', script_content)
cleaned_script = re.sub(r'\s+', ' ', cleaned_script).strip()
chunks = text_splitter.split_text(cleaned_script)
```

3. **用命名实体识别（NER）识别角色实体**：电影剧本有个共同结构——角色名通常是大写字母，这让识别相对容易，用正则表达式实现：

```python
# 模式1：以角色名(全大写)开头的行，后跟冒号或换行
char_pattern1 = re.findall(r'^([A-Z][A-Z\s]{2,20}?)(?::|$)', script_text, re.MULTILINE)
characters.update([name.strip() for name in char_pattern1 if len(name.strip()) > 2])

# 模式2：括号里的角色名，如"(JOHN enters)"
char_pattern2 = re.findall(r'\(([A-Z][A-Z\s]{2,15}?)(?:\s+[a-z]|\))', script_text)
characters.update([name.strip() for name in char_pattern2 if len(name.strip()) > 2])
```

用这些正则表达式提取出的部分角色名不准确，所以还加了一些临时的手工处理逻辑让结果更稳健：**任何有效的角色名必须在剧本里出现至少三次**；**去除一些容易被误识别为角色名的常见词**（如THE、AND、WITH、HIM等）。**这恰恰说明了构建（和维护）知识图谱是件难事，需要领域专业知识**——不像电影剧本这种有全大写角色名这种可预测格式和清晰线索的数据，企业数据（客户合同、工单、系统日志）通常杂乱得多、格式不一致得多，弥合这种"干净结构化示例"和"真实世界数据的模糊性"之间的鸿沟，正是KG构建仍是高投入工作的原因（本章后面详细讨论）。

4. **构建图中的关系**：把`Chunk`节点连接到`Movie`节点和`Character`节点。比如从《黄金眼》这部电影的一个chunk里，提到了KOLKHAZHNA、MARINA、BOND三个角色，就为每个添加以下关系：

```cypher
(Chunk)-[:MENTIONS]->(Character)
(Character)-[:APPEARS_IN]->(Movie)
```

对IMDb数据集，则加入额外的节点（`Person`、`Movie`、`Character`、`Genre`）和关系：

```cypher
(Person)-[:DIRECTED]->(Movie)
(Person)-[:ACTED_IN]->(Movie)
(Movie)-[:HAS_GENRE]->(Genre)
(Character)-[:PORTRAYED_BY]->(Person)
```

最终得到一个整合了电影剧本chunk/元数据与IMDb额外信息/关系的完整知识图谱（完整代码见`create-graph.ipynb`）。

### 在查询时使用知识图谱：两种模式

**模式一：Chunk enrichment（chunk增强）**

检索流程从标准向量搜索开始，找到语义上最相关的chunk。但原始chunk文本经常包含"单薄"的引用——拼错的名字、或"he"这样的代词——缺少LLM给出准确答案所需的完整上下文。用KG对文本中找到的实体做图查找，动态地丰富这些chunk。

书里的例子：查询"哪个角色说了'They call it a Royale with Cheese'，这是哪部电影？"向量搜索成功找到含这句台词的chunk（来自《低俗小说》），但这个chunk里只有角色名Vincent，没有电影名，也没有演员名——LLM单独拿到这段文字很难回答这个问题。**Chunk增强步骤**识别chunk文本里的实体`Character: Vincent`，用KG获取文本里没有的额外上下文：

```
Character: Vincent -> IS_REAL_NAME: Vincent Vega
Character: Vincent -> PLAYED_BY Actor: John Travolta
Character: Vincent -> APPEARS_IN Movie: Pulp Fiction
```

不是只把原始chunk文本发给LLM，而是发送一个包含这些额外信息的**"知识上下文"包**，让LLM能以100%的确定性作答，把一段模糊的片段转变成一个数据丰富的事实。**Chunk enrichment凸显了KG作为高保真"上下文提供者"的优势——它给向量检索的结果做批注、添加结构或元数据。**

**模式二：Hybrid-graph retrieval（混合图检索）**

这种方式先让LLM把用户的自然语言问题直接翻译成正式的图查询语言（Cypher或SPARQL），从图数据库执行提取相关chunk，再和向量检索出的chunk合并。**要让这一步成功，LLM必须先拿到图的schema**——可用的节点标签（如`Person`、`Movie`、`Chunk`）、关系类型（如`:DIRECTED`、`:ACTED_IN`）、属性的一份蓝图。这份schema给了LLM生成合法图查询所需的"词汇"和"语法"。

书里的例子：查询"《黄金眼》里都有哪些角色？其中哪些和邦德有互动？"给了schema后，LLM可以把这个问题翻译成一个Cypher查询（先找《黄金眼》里的所有角色，再找和邦德在同一个chunk里被提及的其他角色）。执行这个Cypher查询检索到相关chunk，直接送进RAG流水线的生成式LLM。如果只用向量搜索检索出的chunk，信息不够，RAG会回答"我无法回答这个问题"；但把向量搜索的chunk和图数据库的chunk结合起来一起送给生成式LLM，就能得到一份详尽的回答——列出《黄金眼》里的所有角色，并具体分析了哪些角色和邦德有过互动（Marina在多个场景、Trevelyan直接对峙、Xenia作为反派等等）。

**这种方式把语义（向量）搜索的概念理解能力，和KG的事实精确性结合起来**，能让RAG应用回答比单靠任何一种方法都更广泛、更准确的问题范围。书里提到，**HippoRAG**这个把LLM和KG结合的图增强RAG框架，在多跳问答基准上比标准RAG基线高出约20%的准确率。

### 如何在两种模式之间选择

Chunk enrichment和hybrid-graph retrieval都利用了知识图谱的力量，但解决的问题不同、运维成本也不同：

- **Chunk enrichment是"元数据优先"策略**：假设你的向量搜索本身已经能有效找到相关文本，只是这段文本本身缺少更宽泛的上下文。适合"查询本身是语义型的（比如问电影里的某句具体台词），但答案需要片段之外的外部事实（比如演员的名字）"这种场景。因为这只涉及对已检索chunk ID做一次简单的索引查找，延迟增加可以忽略不计，生产环境下高度可靠。
- **Hybrid-graph retrieval是"发现优先"策略**：在用户查询本质上是结构化或关系型、需要系统遍历向量搜索会漏掉的连接时表现出色（比如"找出所有和邦德在三个以上场景里互动的角色"）。但这种能力伴随着不小的生产复杂度——你必须管理一套"文本转Cypher"流水线，让LLM把自然语言翻译成数据库查询，这也带来额外风险，比如LLM可能生成幻觉出的无效语法，要安全运行还需要考虑查询超时和重试策略。

两者的主要差异如下表：

| 特性 | Chunk enrichment | Hybrid-graph retrieval |
|---|---|---|
| 主要目标 | 给特定文本片段补充上下文 | 发现关系/聚合信息 |
| 最适合 | 事实性 grounding（日期/姓名/ID） | 多跳推理（谁见过谁？） |
| 运行时风险 | 低：简单索引查找 | 更高：查询幻觉或慢join |
| 延迟 | 极小(亚毫秒级查找) | 可变(取决于LLM和查询复杂度) |
| 实现难度 | 直接，适合最小可行产品 | 复杂，需要"文本转Cypher/SPARQL"调优 |

不管用哪种模式，KG的成功都取决于你的数据工程成熟度。生产环境里会遇到**"实体爆炸（entity explosion）"**——同一个实体因为不同的写法被映射成多个节点（比如你的提取流水线可能给"007"、"James Bond"、"Bond"分别建了三个不同的节点，而不是合并成一个）。构建和维护一个高保真的KG是不小的"离线"工程投入，需要和"用KG提升查询准确率带来的收益"权衡。**最常见的方式是先用评估（第六章）判断哪些查询失败、判断KG能否帮上忙**，如果你刚起步，chunk enrichment通常"投入产出比最高"，能以较低风险提供直接的事实性grounding；随着用例演进到复杂推理和跨文档聚合，投资hybrid-graph流水线才可能变得必要。

另一个重要的实现决策是**向量嵌入存在哪里**：现代图数据库支持原生向量索引，可以直接把embedding存进每个chunk节点的`chunk.embedding`属性里，这样检索流程能在**单次数据库事务里**同时做语义搜索和图遍历，提供原子一致性和单一真相来源——但代价是你现在依赖向量库对embedding的处理，这可能和复杂图遍历竞争RAM，在超大数据集上可能造成性能瓶颈。另一个选项是维持标准RAG检索流程、把embedding存在专门的向量库里——一旦检索到一个chunk，系统用`chunk_id`去图数据库里做增强或进一步遍历的查找。这种方式让你能独立维护高性能的检索流水线（可能还包含混合检索/重排序）和图遍历（支持深度逻辑），**但你现在要负责确保向量库和图数据库完全同步**，避免RAG流程检索到一个已经在图里不存在的chunk、造成应用错误。

## 四、构建知识图谱

前面用IMDb和MovieSum构建电影KG时的一般方法是：**先设计图schema**（决定包含`Person`、`Movie`、`Character`、`Genre`、`Chunk`这些节点，以及`ACTED_IN`、`PORTRAYED_BY`、`DIRECTED`这些关系）→ **再对两个数据集做定制化预处理**来填充图本身。

对电影剧本，能通过识别脚本里的角色名把这个过程部分自动化（因为剧本里角色名相对容易识别）；即便如此，依然要做一些手工处理去移除被误识别成角色名的词（如"her"或"his"）。IMDb数据集本身已经被创建和清洗过了，所以基于该数据集建图相对容易——数据集的创建者已经替你做完了苦活。

**虽然电影剧本这个案例需要人工干预，但它其实还代表了数据提取里的"最佳情形"。** 从企业内部数据构建KG，意味着要在一片"暗数据"（非结构化、格式不一致、散落在各个孤立遗留系统里）的迷宫里导航。如果清理几份电影剧本都感觉繁琐，试想在数百万份碎片化的PDF、电子表格、邮件和私有数据上执行同样的流程，其中领域专业知识是绝对必要的。

### 自动化知识图谱构建

手工精心构建的知识图谱能产出干净、准确的结果，但这种专家驱动的方式劳动密集，很快会成为一个重大瓶颈——**构建KG的过程实际上很难扩展到满足现代企业应用（尤其是动态的RAG和智能体系统，需要处理持续不断涌入的新非结构化信息）的需求**。

因此，用自动化方式从文本构建图正变得更普遍，遵循三个步骤：

1. **找出关键"事物"（实体识别）**：扫描文本，找出并归类重要的名词。比如识别"Apple"是"组织"、"Steve Jobs"是"人"。这些"事物"成为图里的节点。
2. **找出连接（关系提取）**：分析句子，找出这些事物之间的关系。比如处理句子"Apple was founded by Steve Jobs"，可能创建一条连接：`(Apple, FOUNDED_BY, Steve Jobs)`。
3. **清理重复项（实体链接）**：最后系统清理数据，确保同一件事物的不同名称都指向同一个条目/节点。比如系统学习到"Apple"、"Apple Inc."和"the company that makes iPhones"都是同一个实体。这确保图是准确、无重复的。

这整个流程有效地把一片杂乱的文本海洋，转变成一个干净、有组织的互联事实网络。

**用LLM，这几个步骤能被极大简化**：不用为每个任务分别用专门的老式NLP模型，可以用一个强大的LLM读文档，直接输出一组结构化的实体-关系三元组。这种方式简化了工程复杂度，往往还能因为LLM广博的世界知识和细腻的上下文理解而提升结果质量。

**但即使LLM能大幅简化这一步，也要节制预期：纯LLM驱动的三元组提取依然是噪声的、且高度依赖领域**。生产环境里，纯LLM流水线通常只是引导构建一个图的起点，要达到业务成果所需的高保真度，多数团队会实现一套**混合提取策略**——用LLM提议实体和关系，再让这些提议经过一层确定性启发式规则（比如用正则表达式识别ID或日期）、经典NLP模型验证，以及针对关键实体的人在回路界面，做专家质量把关。

### 实体链接：一个关键挑战

用LLM时，一个关键的持续挑战是**实体链接**。真实世界的企业数据是杂乱不一致的，同一个真实世界的"事物"可能被许多不同的名称或标识符引用。这个"一物多名"问题几乎在任何企业知识图谱里的任何实体上都会出现，书里举了几个例子：

- **金融服务里的公司实体**：一家公司可能在新闻文章里叫"IBM Inc."，在监管文件里叫"International Business Machines Corp."，在内部报告里叫"I.B.M."，或者干脆就叫"IBM"。
- **制药领域的药物成分**：一款药经常被它的商品名（如"Tylenol"）、通用/活性成分名（如"acetaminophen"）、正式化学名（如"N-acetyl-para-aminophenol"）分别指代。
- **供应链和电商里的产品**：一件商品比如"iPhone 15 Pro 256GB"，可能在不同供应商或系统里被列成"Apple iPhone 15 Pro (256)"或"IP15PRO-256-BLK"。

要有效解决实体链接问题，需要先定义一个清晰的**本体**，明确你领域里存在哪些"事物"（类，如"人"、"公司"、"药物"）以及它们能有哪些属性和关系。在实体链接的语境下，本体提供了解决"一物多名"问题所需的基本结构——比如它可能规定一个公司实体有一个规范名称（如"International Business Machines Corp."），同时也有一份别名清单（如"IBM"、"I.B.M."）。系统之后遇到"IBM Inc."时，就知道自己的任务不是创建一个新节点，而是把它识别为一个别名并链接到已有的规范公司节点，按schema定义填充相应属性。

有了本体作为目标结构，实体链接过程需要主动地匹配、链接、合并实体。这很少是单一的算法或方法，而通常是一条多阶段流水线，典型包含两个步骤：

1. **归一化（Normalization）**：清理并标准化原始文本（比如"Corp."和"Corporation"都统一成"corp"；全部转小写）。
2. **候选生成（Candidate generation）**：找可能代表同一"事物"的实体时，通常先以某种方式缩小搜索空间，避免拿每个实体去和其他所有实体比较——比如只对比人名实体，用**Jaro-Winkler距离**（衡量"Chris"和"Christopher"这类字符串的相似度）这类简单字符串比较技术，到更复杂的上下文/领域特定相似度指标。

完整的实体链接流程通常有一个初始的**引导阶段（bootstrapping phase）**——对现有数据跑一次大规模作业，创建初始的一套规范实体集合。之后常用**增量模式**——每当新的非结构化数据到来，实体链接模型的任务就是把新的表面形式（如"Tylenol"）和图里现有的规范实体（"acetaminophen"对应的Drug节点）做匹配。这个过程也可以配合**人在回路**增强——当系统对某次匹配的置信度较低时（比如"Christian"是不是等于"Christopher"，五五开），就把这个歧义标记出来交给专家审核，让稀缺的人工精力只聚焦在最难的案例上，系统边运行边从专家反馈中持续学习改进准确率。

**实体链接（在计算机科学文献里也叫记录链接/record linkage）在大规模、数据杂乱的场景下尤其具挑战性**，凸显了即使借助LLM的强大能力，从文本自动化生成知识图谱依然存在固有的困难。

### 借助标准本体和知识图谱

从零构建知识图谱是一件高风险的事——书里引用一位有几十年知识图谱构建经验的专家给出的估计：**超过50%的此类项目会失败**。技术上的原因常常是低估了涉及的复杂度（尤其是实体链接部分），另一个常见原因是试图对整个领域建模成"万能图"，而不是采用聚焦、用例驱动的方式。

标准本体能提供一个"抢跑优势"，帮你避免这个陷阱——它们提供针对特定领域（如金融或医疗）关键概念和关系的正式、标准化结构。通过借助本体，你不仅节省了开发时间，还能确保数据模型正确、一致、可互操作，避免建出一个过于宽泛、无法使用的图这个常见陷阱。

有几个强大的开源本体可以直接用：**金融行业本体（FIBO）**，由企业数据管理（EDM）理事会开发，为`Corporation`、`Security`、`Loan`这类金融概念提供了精确的词汇表——它的价值在于其详尽、标准化的属性，这些属性对准确的实体解析至关重要。

用本体给你的是知识图谱的蓝图，但你依然需要用数据把它填满。像**Dun & Bradstreet**、**Refinitiv（现LSEG）**、**S&P Global**这样的公司，投入了数百万小时做实体链接的困难工作，最近正通过策划好的数据源分发这类数据，为实体分配规范标识符（比如**Data Universal Numbering System（D-U-N-S）**编号或**Permanent Identifier（PermID）**），唯一标识实体并映射它们复杂的公司层级关系。

类似地，医疗健康领域，**DrugBank**这类数据集充当一份全面的知识图谱，映射药物与化学成分之间的关系——比如"阿托伐他汀"这个药物实体，通过特定关系连接到它已知的蛋白靶点（如HMG-CoA还原酶）、代谢它的酶（如CYP3A4）、以及它和其他药物之间的相互作用。

**授权使用这类数据的核心价值在于：提供一个高质量、已预先解析好的核心知识图谱，让你免去自己解决一切问题的巨大工作量**。你的任务被缩减成一个小得多、更可控的问题——把你新增的、杂乱的内部数据链接到供应商已建立好的规范实体上，让你能把系统里的"IBM"或"I.B.M."都连接到"International Business Machines Corp."的那一条黄金记录上。**但这类可授权的KG虽然有价值，也有其代价：除了授权费本身，你还要考虑使用这种特定形式KG所带来的绑定，以及你所有其他数据系统都要与之兼容的承诺。**

### GraphRAG

鉴于构建和维护KG的巨大复杂度，研究者一直在寻找其他把KG整合进RAG的方式，其中之一是微软的**GraphRAG**——一种创新方法，用LLM不只提取原子事实，而是生成一个能捕获多个抽象层级信息的**层级化图谱**。

**需要澄清术语**：一些AI工程师用"GraphRAG"泛指任何形式的图辅助RAG（比如前面讲的手工构建KG的技术）。但本章特指微软研究院提出的、专门用于支持"**sensemaking查询**"的具体方法——"sensemaking查询"指的是宽泛的、探索性的查询，需要综合整个数据集的信息才能回答，比如"所有邦德电影里的主要主题是什么？"。技术上，这个过程叫**查询聚焦摘要（query-focused summarization, QFS）**——目标是基于对数据的全局视角生成一个全面的答案，而非检索少数几个可能覆盖不到这种全局视角的具体片段。

**GraphRAG工作原理**：

1. **构建知识图谱**：用LLM从非结构化文本语料自动提取关键实体（如人、地点、概念）以及它们之间的关系。这个图不基于预定义的schema，而是源文档本身知识内容的一种直接结构化表示，捕捉文本中不同思想和实体是如何互相关联的。
2. **社区检测（Community detection）**：GraphRAG的核心创新在于它如何利用这个新建的知识图谱。不是把它当普通的KG处理，而是应用**社区检测算法**去识别"密集连接的实体簇"。这些"社区"代表你数据里的核心主题和语义话题，随后GraphRAG用LLM为每个社区生成多个层级的摘要——从非常具体的子话题到宽泛的总体主题。
3. **查询**：响应用户的sensemaking查询时，GraphRAG查询引擎不像普通RAG那样直接搜索原始文本、再用LLM总结。而是找到能回答该查询的最相关社区摘要，用LLM基于每个相关社区摘要生成一个部分答案，然后再用另一次LLM调用把这些所有部分答案综合成一个针对该查询的最终、全面的回答。

### 用GraphRAG实操（对应 `chapter9/graphrag-create.ipynb` 和 `chapter9/graphrag-query.ipynb`）

微软的`graphrag`包是开源的，用MovieSum数据集演示：

```python
from datasets import load_dataset
moviesum_dataset = load_dataset("rohitsaxena/MovieSum")
moviesum_df = pd.DataFrame(moviesum_dataset['train'])
```

因为GraphRAG索引阶段调用大量LLM，成本和耗时都不小，所以只挑20部电影做示例：

```python
np.random.seed(42)
SAMPLE_SIZE = 20
indices = np.linspace(0, len(moviesum_df) - 1, SAMPLE_SIZE, dtype=int)
filtered_df = moviesum_df.iloc[indices].copy()
```

**这20部电影的GraphRAG索引成本约$6.32；如果用完整的1800部电影数据集，成本会超过$560**——书里提醒，如果换成你整个Google Drive或Microsoft SharePoint账户的规模，成本会有多恐怖可想而知。

定义好`settings.yaml`（配置用哪个LLM、chunk大小、图实体类型等）后，跑索引只需调用库函数：

```python
from graphrag.api import build_index
from graphrag.config.load_config import load_config

config = load_config(root_dir=GRAPHRAG_DIR)
results = await build_index(config=config, input_documents=input_df, verbose=True)
```

**这个过程会花不少时间**——书里提到在一台配置不错的M4 Mac笔记本上，仅仅20部电影就跑了约45分钟，因为GraphRAG索引不是一次性简单处理，系统要对每个文本chunk做大量连续的LLM调用：先提取实体和声明，再解析合并这些实体，最后生成多层级的社区摘要——每一步都计算昂贵，即使是20部电影这种小数据集也会累积出很大的延迟。

GraphRAG生成一个`output`文件夹，包含若干Parquet文件（`entities`、`relationships`、`communities`、`community_reports`、`text_units`）。GraphRAG定义两种查询函数：

- **local_search**：探索性的"自底向上"方法。先在图里定位几个和查询紧密匹配的种子节点，再沿边"走出去"发现附近、上下文相关的邻居节点和关系（比如1跳或2跳邻居）。适合回答具体、详细的问题，所需上下文很可能就在图的一个局部"邻域"内。
- **global_search**：全面的"自顶向下"策略。不是从种子节点展开，而是在整个图里搜索所有语义上和查询概念相关的节点、关系甚至整个子社区，即便它们彼此并不直接相连。更适合需要综合多个、可能互不相连的图各部分信息的宽泛、高层级查询。

对全局搜索查询"所有电影剧本里的主要主题和叙事模式是什么？"，得到的回答是一份综合性的分析，涵盖：**冲突与斗争**（物理军事冲突、个人社会对抗、超自然战斗）、**家庭与人际关系**（亲子纽带、复杂家庭挣扎、人际网络）、**超自然与灵异元素**（附身与闹鬼、心理恐怖与创伤、神秘魔法冲突）等主题，每个论点还附带具体的报告编号作为数据引用支撑。

尽管GraphRAG在回答这类困难的sensemaking问题上很有优势，**它最主要的缺点是前期预处理的高昂成本（和耗时）**。标准RAG系统只需要切分文本和生成向量嵌入，是一个相对快速廉价的过程；而GraphRAG要经历一套多阶段、计算密集的预处理流水线——需要一个强大的LLM先读完整个语料提取实体和关系、构建一个庞大的知识图谱、对这个图跑复杂的社区检测算法，最后再用LLM为每个已识别的主题生成层级化摘要。

**因为这种开销，GraphRAG在以下几种常见生产场景里往往是错误的工具选择**：

- **快速变化的语料**：对于频繁更新的数据（新闻源、支持工单、活跃的代码仓库），持续重新计算社区摘要在财务和运维上往往不切实际。
- **延迟敏感或个性化查询**：综合多个社区摘要的过程天生比标准向量查找慢，不适合需要亚秒级响应或针对特定用户私有数据定制的应用。
- **需要逐字引用**：GraphRAG擅长高层级抽象。如果你的用例需要LLM提供文档里逐字（原始）的句子用于审计或法律合规，社区报告的摘要性质可能"损失"太多细节，太"lossy"。

**最终，如果你的查询大多是简单的事实检索（比如"X的价格是多少？"），GraphRAG提供的显著投入相对标准语义搜索几乎没有ROI。**

## 五、图数据库基础设施

把知识图谱整合进RAG应用不只是一个架构决策，更是一项长期的运维和系统级承诺。高精度、可解释答案的潜力很大，但构建、扩展、尤其是维护图数据库的复杂度同样很大。

### 图数据库的几种类型

- **传统服务器/集群（如Neo4j、TigerGraph）**：可以像传统SQL数据库一样，把这类系统作为有状态、独立的服务运行在专用虚拟机或Kubernetes集群里。这种情况下，DevOps团队要对一切负责：安装、配置、集群化、分片、资源管理、网络安全。规模化设计至关重要，因为属性图通常受内存限制，性能取决于能否把"热图"塞进RAM里。**适合有严格的本地部署/监管约束、或需要对数据库引擎做深度底层定制的场景**（托管服务通常不允许这种定制）。
- **托管云服务（如Neo4j AuraDB、Amazon Neptune）**：用平台即服务的方式，你用精细控制换取运维简便性，云厂商处理打补丁、备份、高可用，负担从服务器管理转移到成本管理和身份访问管理（IAM）集成。**适合需要多租户访问、高可用、自动化备份，但缺乏内部图数据库专业知识或专职DevOps资源管理集群的场景。**
- **嵌入式库（如Kuzu、DuckDB）**：更新的"无服务器"模型，数据库就是运行在应用进程内部的一个库，"数据库"就是磁盘上的一个文件。这里传统的服务器管理员角色消失了，挑战变成数据生命周期和构建管理——如何在运行中的应用容器里更新静态的图文件？这需要一套健壮的CI/CD流水线，能构建新的数据文件、打包进新的容器镜像、推出部署。**适合KG相对小（10-20GB以内）、以只读为主、能通过CI/CD流水线刷新的场景**，挑战在于数据生命周期——把新的图文件打包进容器镜像用于部署。

### 日常运维的几个主要挑战

- **ETL**：这是最容易被低估的成本。一个"过时"的图就是一个"没用"的图，你需要构建可靠的ETL流水线确保KG保持最新。生产环境里，这条流水线必须解决**数据完整性**问题——因为从多个来源构建一张图涉及一连串操作，你面临如果某次导入中途失败就得到一个"破损"图的风险（比如电影剧本chunk导入了，但IMDb元数据同步崩溃了）。传统SQL数据库靠事务确保**原子性**（"全有或全无"），但把整个图"构建"包进一个事务往往不可行——会锁住数据库数小时、耗尽内存。取而代之的是，使用KG的生产RAG系统可以设计成**幂等的（idempotent）**——如果摄取代码失败并重启，结果应该和第一次就成功一样。在Cypher里，这通过用`MERGE`而非`CREATE`实现——数据库在添加实体前先检查其是否已存在。通过把幂等性和批处理结合（每1000个节点提交一次，而非整个图一次性提交），你转向一种**最终一致性（eventual consistency）**模型，能更有韧性地应对生产企业数据的杂乱现实。
- **模式刚性与演进**：虽然图数据库常被宣传为"无模式"，一个RAG系统需要可预测的结构才能生成合法的Cypher或SPARQL查询。不同于SQL，多数图数据库缺少简单的`ALTER TABLE`命令，所以当你的领域演进时（比如增加新的关系类型或拆分一个实体），你必须管理**实时迁移（live migrations）**——运行后台脚本在不停机的情况下重构数百万节点和边。你可能还需要考虑**模式版本管理**，确保LLM的查询生成逻辑和数据的当前状态保持同步。
- **性能**：一次多跳图遍历（比如"找出所有和CEO住在同一城市、评论过同一产品的用户"）延迟可能变化很大，取决于查询的深度和图的结构（比如是否命中一个"超级节点"）。由于多数图是内存密集型的，配置足够RAM的合适硬件、确保能纵向和横向扩展至关重要。这往往是一项相对专门的技能：团队需要学会剖析Cypher/SPARQL查询、识别瓶颈、管理索引（标准索引和向量索引都要）、并可能需要重构图的部分结构以避免"超级节点"热点。
- **安全、备份与高可用**：和任何有状态数据库一样，图数据库也需要健壮的灾难恢复计划，配合自动化、经测试的备份恢复流程。但图驱动的RAG系统里，安全性比标准的静态加密还要多一层复杂度——因为图往往综合了来自不同来源的数据，你的基础设施必须支持RBAC，这可能需要在节点或关系级别实现——比如确保一个LLM能遍历一个`Company`节点，但被限制访问关联的`Employee`节点上的`Salary`属性。

维护开销是图数据库一项持续且经常被低估的运维成本。核心挑战始终是**确保数据新鲜度和一致性**：源数据一变化，图就必须相应更新。

### 图更新模式与演进

生产环境里，源数据很少是静态的。保持KG和活数据同步，需要超越"整体重建"方式，转向增量维护，通常有两种主要模式：

**摄取策略：CDC vs 事件驱动**

- **变更数据捕获（CDC）**：如果源数据存在传统数据库里（如Postgres），可以用CDC工具（如Debezium）监听数据库的事务日志，每当有行被创建/更新/删除时触发一个事件，这些事件随后被映射成Cypher的`MERGE`或`DELETE`命令，作用到你的KG上。
- **事件驱动架构**：对非结构化数据（新PDF文件或聊天记录）来说，事件驱动模式更受青睐。当新文档进入你的存储（如S3），会触发一个无服务器函数（如AWS Lambda），只对这份特定文件跑LLM抽取流水线，把新的节点和边追加进已有的图。

**处理实体合并**：长期运行的KG里一个常见的边缘情况是，两个先前被认为不同的实体，后来发现其实是同一个（比如"Twitter"和"X"）。要处理这种情况，你需要实现一套"合并"逻辑——把一个节点的关系重新映射到"幸存"节点上（另一个节点被删除）。

另一个挑战是当事实"过期"。比如一个人离职后，`WORKS_AT`这条关系不应该直接删除（为了保留历史上下文），而应该被打上"墓碑（tombstoned）"标记，比如`status: "inactive"`标签，之后你的RAG查询需要相应更新，过滤只保留`:WORKS_AT {status: "active"}`。

**维护一个"活的"KG需要同时实现能捕获实时数据变化的自动化摄取流水线，以及处理身份冲突、管理老化事实相关性的内部生命周期逻辑。**

## 六、准确率/成本权衡

构建RAG应用时会面临一个根本性的架构选择：坚持用"vanilla"（普通）RAG，还是投资整合知识图谱。这是一个经典的工程权衡——普通RAG相对低成本、简单，对比的是知识图谱带来的、可能的但不保证的准确率提升。在承诺走图方案之前，理解你具体的KG投入产出比、以及你实际能看到的准确率提升是否值得增加的成本和复杂度，非常重要。

**别低估普通RAG**：对很多应用来说，它可能已经足够满足需求，不需要任何额外的复杂度，实现相对直接，运行成本也划算。对通用问答或对大量文档集做摘要这类场景，找到"方向大致正确"或"语义相关"的上下文，就足以让LLM给出高质量回答。

实现GraphRAG或本章讨论的任何一种KG整合方式，都不是一个小的附加项，而是一项重大承诺——成本不只是财务上的，更是对开发和运维资源的沉重税负。你需要在图数据建模上大量投入、搭建并维护新的图数据库基础设施、构建并维护复杂的数据流水线来创建和保持图随源数据演进而更新。**这份持续的维护负担经常被低估，可能成为显著的资源消耗**。诚实评估你的系统是否真的需要这种精度水平，只有你真正看到潜在ROI时才值得投入。

### 决策清单

书里给了一份可操作的清单，帮你判断是否值得引入KG——**如果对至少四个问题不能回答"是"，那KG的运维"税"可能超过它带来的收益**：

- **事实性失败**：我们的评估里，是否有反复出现的多跳、时间限定、或高度约束性的查询，是普通RAG或混合RAG始终失败的？
- **grounding必要性**：这个用例是否要求对特定实体做100%确定性的grounding（比如法律合规或医疗剂量），而"概率性"相似度风险太高？
- **可用资产**：是否有现成的本体资产（一份可授权的KG如DrugBank或LSEG，或一个标准本体如FIBO）可以借用，避免从零开始构建？
- **数据连接性**：我们的数据是否天然适合图结构？（也就是说，价值是不是在于文档之间的关系，比如企业层级或供应链依赖，而不是文档本身的内容？）
- **长期所有权**：我们是否有一支团队，有能力长期负责图数据建模、模式演进、复杂ETL流水线？
- **业务ROI**：预期的准确率提升，是否和明确的业务成果相关联，比如降低风险、确保合规、或解锁新的营收功能？

## 七、本章小结

本章介绍了在RAG中使用知识图谱的思路，目标是为KG最擅长回答的那类查询实现更高质量的回答。向量搜索或混合搜索擅长理解概念型查询，但面对包含时间限定事实、多跳逻辑或重叠约束的问题时可能力不从心。知识图谱恰恰擅长回答这类问题。通过把KG整合进RAG（无论是通过chunk enrichment还是hybrid-graph retrieval），你能让RAG应用以更高的准确率回答更复杂的问题。

**但这项进步不是免费的**：它要求在数据建模、实体链接、摄取流水线和基础设施上投入相当可观的资源，迫使你在检索准确率和运维复杂度/成本之间做出关键权衡。

在RAG中使用KG是一个正在演进的领域，其未来在于把那些让它如此有挑战性的瓶颈自动化。手工构建图这个繁琐的过程，正在让位于LLM驱动的流水线（能高效提取实体和关系，前提是有健壮的验证层和人工监督来兜底）。知识增强RAG的未来在于把这些瓶颈自动化，同时维持一个能随业务需求变化而演进自己的schema和逻辑的"活的"图。微软的GraphRAG是一个典型代表——用LLM直接从源文档构建图，但微软这个具体实现可能引入不小的成本和延迟，并不适合每个企业负载。更广泛地说，当图架构是围绕应用的数据模型、查询模式和生产约束设计出来的时候，知识图谱增强RAG可以非常实用。

**实践中，多数团队从标准RAG起步，用评估技术（第六章）识别回答质量不足的问题查询，针对那些查询再去试点知识增强RAG或GraphRAG。**

书里给出一张贯穿全书的RAG架构对比总结表：

| 方法 | 最适合 | 关键限制 | 成本与复杂度 |
|---|---|---|---|
| 标准RAG（向量搜索） | 通用问答、基于相似度的检索、非结构化文本 | 可能在多跳逻辑、时间限定事实、硬约束上吃力；可能漏掉与语义不匹配的具体SKU或名称 | 低。构建和维护简单 |
| 关键词混合（向量+BM25） | 平衡语义含义和精确匹配 | 依然在多跳逻辑和深层关系上吃力 | 低到中。需要调优向量和BM25的权重 |
| KG-hybrid RAG | 精确的、多重约束的事实性查询（"哪些CEO也拥有电动车？"） | 需要构建并维护一个最新的KG | 高。需要显著的数据工程投入 |
| Microsoft GraphRAG | 宽泛的"sensemaking"查询（"这1000份文档里的主要主题是什么？"） | 前期处理成本很高，不适合实时数据，缺乏逐字粒度 | 极高。摄取阶段计算成本很高 |
| Agentic RAG | 多跳逻辑和迭代式研究任务 | 高延迟，智能体可能陷入循环或产生工具路径幻觉 | 中到高。需要健壮的编排(如LangGraph等) |

**知识图谱研究社区在持续创新更好、更简单、更具成本效益的方式把KG整合进RAG和智能体工作流，预计这项技术会随时间提供更多价值和更好的ROI。**

## 八、关键术语表（新增）

| 术语 | 大白话解释 |
|---|---|
| 知识图谱(KG) | 用节点(实体)和边(关系)编码事实知识的机器可读网络，查询靠"沿路径遍历"而非"找相似度" |
| Cypher / SPARQL | 两种图查询语言，前者语法直观贴近图结构(Neo4j)，后者是W3C标准用于查询三元组(RDF存储) |
| 本体(Ontology) vs 模式(Schema) | 前者是领域的抽象逻辑规则("Person可以DIRECT Movie")；后者是数据库层面的具体实现(release_year是Integer) |
| Chunk enrichment(chunk增强) | "元数据优先"策略：向量搜索已找到相关文本，用KG补充文本里缺失的外部上下文，延迟极小、高可靠 |
| Hybrid-graph retrieval(混合图检索) | "发现优先"策略：LLM把自然语言翻译成Cypher/SPARQL查询图数据库，和向量检索结果合并，能处理多跳关系但运维复杂度更高 |
| 实体爆炸(Entity explosion) | 同一实体因不同写法被提取成多个节点(如"007"/"James Bond"/"Bond"三个节点)的常见KG问题 |
| 实体链接(Entity linking) | 解决"一物多名"问题，把不同表面形式(如"IBM Inc."/"I.B.M.")匹配链接到同一规范实体节点 |
| GraphRAG(微软) | 用LLM自动构建层级化知识图谱+社区检测+多级摘要，专门支持宽泛"sensemaking查询"(查询聚焦摘要QFS)的方法，区别于泛指的图辅助RAG |
| local_search / global_search | GraphRAG的两种查询模式：前者从种子节点向外遍历邻居(适合具体问题)，后者搜索全图相关社区(适合综合性宽泛问题) |
| 幂等性(Idempotency) | 摄取代码失败重启后结果和第一次成功一样，Cypher里用MERGE而非CREATE实现，是图ETL健壮性的关键 |
| 墓碑标记(Tombstoning) | 事实过期时不删除关系而是打status:inactive标签保留历史上下文的做法 |
| 联邦检索(与第十章相关) | (预告)让查询去源数据所在地，而非把数据都搬进RAG存储的架构思路 |
